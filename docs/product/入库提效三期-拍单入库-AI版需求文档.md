## 1. 背景和目标

当前到货入库需要店员在随货同行单、实物追溯码、码上放心上游单据和掌店易系统单之间反复查找、核对。找单和异常处理耗时，且容易在数量、批号、效期等信息上出错。

三期将拍单、验货、核准放进同一个入库任务：

- 拍随货同行单，OCR 生成拍单明细；
- 扫描追溯码，定位码上放心上游出库明细并聚合对码核准明细；
- 自动匹配掌店易系统单和随货单 OCR 行；
- 高置信且无冲突的明细进入准入库，其余进入待核准；
- 由用户决定何时提交入库。

### 1.1 本期目标

1. 扫描一个追溯码，可定位其所属的码上放心上游出库明细，并得到应录追溯码。
2. 尚未产生入库结果时，同一上游明细的追溯码聚合到同一条对码核准明细，持续维护应录、实录。
3. 自动匹配系统单明细和随货单 OCR 行，给出唯一匹配、多候选、无匹配和字段冲突。
4. 自动放行明确一致的明细，把需要人判断的内容集中到核准页。
5. 支持任务内持续拍单、扫码、核准和入库，不因一次提交入库而封口。

### 1.2 本期不做

- 不新增“找采购单”步骤；
- 不在验货页展开复杂匹配原因；
- 不写状态卡点击后的详情页需求；
- 不把 Demo 的模拟数据和前端临时逻辑当作生产规则；
- 不在本文确定数据库表、索引和技术存储方案。

## 2. 入库任务

### 2.1 任务定义

入库任务是一次可持续进行的拍单入库工作会话，用于承载随货单图片、拍单明细、扫描追溯码、对码核准明细、候选系统单和入库结果。

任务无边界、无完成态：

- 一个任务内允许处理多张随货单、多个供应商、多个系统单和多批商品；
- 允许持续新增图片和追溯码，也允许多次提交入库；
- 业务上建议按一次或一批到货拆分任务，但系统不限制任务规模，不自动封口；
- 已有明细入库后，任务仍可继续拍单、验货、核准和入库；
- 任务列表统一提供“进入”，不因已入库变成不可编辑状态。

### 2.2 主流程

1. 用户新建任务或进入已有任务。
2. 拍照或上传随货单，OCR 成功后生成拍单明细。
3. 用户扫描追溯码，系统定位码上放心上游明细并生成或更新对码核准明细。
4. 系统匹配掌店易系统单明细和拍单明细，计算核准结果。
5. 符合自动放行条件的进入准入库；其余进入待核准。
6. 用户处理待核准明细，可换候选、核准完毕、留在待核准或提报异常。
7. 用户主动提交准入库明细；成功后对应明细转为已入库。
8. 用户可继续在当前任务内重复以上操作。

待验货或待核准明细不阻塞其他准入库明细提交。系统不得因进入准入库而自动执行入库。

## 3. 核心对象和统计口径

### 3.1 核心对象

| 对象 | 定义 |
| --- | --- |
| 随货单图片 | 用户拍照或上传的随货同行单原图，OCR 成功后保留在任务内。 |
| 拍单明细 | OCR 识别出的一条商品行，是待验货的统计对象，也是随货单匹配候选。 |
| 码上放心上游明细 | 由追溯码定位到的上游出库单商品明细，提供商品、批次、效期和应录码集合。 |
| 对码核准明细 | 验货、系统单匹配、拍单匹配、核准和入库的中心对象。 |
| 系统单明细 | 掌店易待收或部分入库的采购商品行，是账面入库依据。 |
| 追溯码 | 用户实际扫描的实物码，同一任务内去重。 |

正常对码核准明细按 bill_code + drug_ent_base_info_id + product_batch_no 聚合。该 key 尚未产生入库结果时，再次扫码只追加追溯码并重算，不新增重复明细。已有入库结果后的处理轮次见第 9 章待确认。后端可为防止物理冲突补充内部主键，但不得改变产品统计口径。

无法定位码上放心商品明细时，必须保留原始追溯码、失败阶段和接口结果，不能丢码。此类记录是否生成异常对码核准明细、是否计入待核准，见第 9 章待确认。

### 3.2 四张状态卡

| 状态卡 | 统计对象 | 计数规则 |
| --- | --- | --- |
| 待验货 | 拍单明细行 | OCR 成功且尚未被对码核准明细匹配/覆盖的有效商品行数量。 |
| 待核准 | 对码核准明细行 | 当前核准结果为待核准的明细数量。 |
| 准入库 | 对码核准明细行 | 自动放行或人工核准完毕，尚未提交入库成功的明细数量。 |
| 已入库 | 对码核准明细行 | 已提交且入库成功的明细数量。 |

补充规则：

- 待核准、准入库、已入库是同一类对象的不同状态，一条对码核准明细同一时刻只计入其中一张卡；
- 准入库明细提交成功时，准入库 -1、已入库 +1；失败时仍留在准入库；
- 待验货和后三张卡不是同一对象口径，四卡之和不是任务总商品数，也不是任务完成率；
- 新增、删除、匹配、核准、提交入库或候选占用变化后，相关卡片实时重算；
- 状态卡点击后的详情页另行补充，本版只定义计数和刷新规则。

待验货中的“已匹配/覆盖”必须基于生效的拍单明细关联，只有候选不算已覆盖；一条拍单明细被部分数量覆盖时如何计数，见第 9 章待确认。

## 4. 核心业务逻辑

### 4.1 单码验货

每次识别到追溯码后，按以下顺序处理：

1. 先按 inbound_task_id + trace_code 去重。任务内重复码不重复计数，提示已扫描，并定位原对码核准明细。
2. 调用 52560，通过 code + 本企业 ref_ent_id 查询该码关联的上游出库单。
3. 若得到唯一上游单据，使用 bill_code、from_ref_user_id、to_ref_user_id、ass_ref_ent_id 调用 53727 查询单据明细。
4. 在 drug_infos_dto_list 中，用扫描码精确匹配 code_info_list_dto_list[].code，定位所属商品明细。
5. 若扫描码未直接命中，调用 52563 查询大小码关系；与应录码集合存在唯一交集时，归入该明细并记录 relation_match。
6. 仍无法定位时，保存原始码、失败阶段和接口错误信息；后续承载对象和计数口径待确认。
7. 定位成功后，创建或更新未入库的对码核准明细，追加实录码并重算实录数量；同 key 已有入库结果时按待确认规则处理。
8. 触发系统单匹配、随货单匹配、应录实录校验、全量核准和状态卡重算。

52566 仅用于补充商品和批次基础信息，不能单独证明上游单据和应录数量。69631 返回码未激活或不存在时，不计入正常实录，进入待核准。

### 4.2 系统单匹配

#### 4.2.1 触发时机

以下变化均需重新匹配：

- 新增或删除追溯码；
- 新建或更新对码核准明细；
- 系统单候选池、订单状态或剩余数量变化；
- 用户替换系统单候选；
- 影响商品、批次、数量的人工操作。

#### 4.2.2 候选过滤

| 条件 | 规则 |
| --- | --- |
| 门店 | 只取当前门店的系统单。 |
| 单据状态 | 只取允许入库的待收、部分入库单据。 |
| 剩余数量 | remaining_qty > 0；先扣除同任务内其他明细已占用数量。 |
| 供应商 | 已绑定码上放心 ref_ent_id 时必须一致，不一致直接排除；未绑定时作为弱候选。 |
| 日期 | 优先取验货日期 T-5 ~ T 内的单据；窗口外可进入低优先候选，但不得自动进入准入库。 |

不满足门店、单据状态、已绑定供应商或剩余数量条件的明细不可选，但需保留排除原因供核准页解释；全部候选被排除时判为无匹配，不再同时作为可选的“硬冲突候选”。

#### 4.2.3 证据集合

三条证据线：

- line1：生产批号精准匹配；
- line2：批准文号去除非字母数字后精准匹配；
- line3：药品名称归一化后互相包含或相似匹配。

候选先按证据集合分级，再在同级内评分。集合优先级高于分数。

| 集合 | 命中情况 | 用途 |
| --- | --- | --- |
| A | 三条证据线全部命中 | 最高优先级。 |
| B/C/D | 任意两条证据线命中 | 中高优先级，可参与自动唯一判定。 |
| E/F/G | 仅一条证据线命中 | 只作为人工候选，不得自动进入准入库。 |
| 无集合 | 三条均未命中 | 无匹配或低置信候选。 |

#### 4.2.4 评分

| 维度 | 分值 | 规则 |
| --- | ---: | --- |
| 供应商一致 | +20 | 已绑定 ref_ent_id 一致为强证据；仅名称相似为弱证据。 |
| 数量一致 | +20 | 实录/拟入库数量与系统单剩余可入库数量一致。 |
| 规格一致 | +20 | 包装规格、制剂规格归一化后一致。 |
| 厂家一致 | +15 | 厂家归一化后一致或明确包含。 |
| 批号、效期一致 | +15 | 系统有值时与码上放心明细一致。 |
| 单据时间命中 | +10 | 单据日期在 T-5 ~ T 内。 |

判定规则：

- 唯一匹配：最高候选属于 A/B/C/D，score >= 85，与第二名分差 >= 15，且无硬冲突；
- 多候选：最高候选达到门槛但分差 < 15，或存在同优先级、无法唯一确定的候选；
- 无匹配：无候选，或最高 score < 60；
- 60 <= score < 85：只进入人工候选，不自动进入准入库。

完整命中按表内分值加分，字段缺失不加分。供应商仅名称相似时的具体分值、批号和效期部分命中时的分值、字段归一化细则尚未明确；依赖这些弱命中才能达到 85 分的候选，在规则补齐前不得自动进入准入库。

硬冲突包括：已选候选的供应商绑定关系变化后不一致、商品身份冲突、系统单状态变为不允许入库、剩余数量变为不足。存在硬冲突时，候选立即失效并重算。

#### 4.2.5 一对一和两行组合

- 默认一条对码核准明细匹配一条系统单明细；
- 仅当两条系统单明细属于同一系统单、同一商品、同一批号，且两行剩余可入库数量之和等于当前明细拟入库数量时，允许两行组合匹配；
- 不允许跨系统单组合，不允许不同商品或不同批号组合，不做三行及以上任意组合；
- 组合条件不满足时进入待核准，不通过凑数自动放行。

两行组合仍对应一条对码核准明细。组合内一行成功、一行失败时的事务和状态卡口径尚未明确，见第 9 章待确认。

### 4.3 随货单匹配

#### 4.3.1 触发和候选池

OCR 完成、对码核准明细变化、图片/拍单明细删除、用户替换拍单候选后，重新计算随货单匹配。

候选池为当前任务下所有有效拍单明细。低置信 OCR 行可以进入候选，但不得自动进入准入库。

#### 4.3.2 匹配规则

| 维度 | 规则 |
| --- | --- |
| 批号 | OCR 批号与码上放心批号完全一致，为强证据。 |
| 批准文号 | 归一化后完全一致，为强证据。 |
| 名称 | 相似度 >= 60% 可进入候选；自动命中需 >= 80%，且至少有一项其他强证据。 |
| 数量 | 拍单数量与应录/实录数量一致；不一致进入待核准。 |
| 规格 | 与包装规格、制剂规格归一化匹配。 |
| 厂家 | 厂家全称、简称归一化后匹配。 |

结果判定：

- 唯一匹配：批号或批准文号至少一项强命中，名称、规格、数量无硬冲突，且候选唯一；
- 多候选：多条拍单明细满足条件，或同商品同批在多张票中出现；
- 无匹配：没有可靠拍单明细；
- 低置信：OCR 置信度低、关键字段缺失或局部截图定位异常。

多候选、无匹配、低置信均进入待核准。

### 4.4 全量核准

核准以对码核准明细为中心，对比码上放心、掌店易系统单和随货单 OCR 三方数据。

| 核准项 | 规则 |
| --- | --- |
| 供应商 | 已绑定 ref_ent_id 冲突为硬冲突；未绑定时按名称弱匹配。 |
| 商品身份/批准文号 | 双方有值且不一致，不得自动放行。 |
| 名称 | 归一化后校验；批准文号已确认同商品但名称有差异时可降为提示。 |
| 规格 | 包装规格、制剂规格冲突进入待核准。 |
| 厂家 | 归一化后校验，冲突进入待核准。 |
| 批号 | 有值且冲突进入待核准；系统单缺失时展示缺失。 |
| 生产日期 | 有值且冲突进入待核准。 |
| 效期 | 有值且冲突进入待核准；近效期、过期规则待确认。 |
| 数量 | 应录、实录、拍单数量和系统单剩余数量不一致，进入待核准。 |
| 条码、品牌 | 弱核准项，缺失不阻断；明确冲突需提示。 |
| 单价、金额 | 默认展示差异；是否阻断入库待确认。 |

自动进入准入库必须同时满足：

1. 码上放心上游明细定位唯一；
2. 应录实录校验通过；
3. 系统单唯一高置信匹配；
4. 随货单唯一高置信匹配；
5. 无硬冲突；
6. 未标记破损，无人工提报异常。

任何一项不满足，进入待核准并展示明确原因。

### 4.5 应录、实录

| 场景 | 判定 | 处理 |
| --- | --- | --- |
| 全部正常 | 实录码去重后均属于应录码，且实录数量 = 应录数量 | 校验通过，继续全量核准。 |
| 少扫 | 实录码均属于应录码，但实录数量 < 应录数量 | 待核准，提示还差 n 个追溯码。 |
| 多扫/混扫 | 存在不属于当前上游明细的码 | 可定位的归入正确明细；不可定位的保留为扫码异常记录；当前明细重算。 |
| 重复扫 | 同一任务已有相同追溯码 | 不计数，提示已扫描并定位原明细。 |
| 无应录码集合 | 53727 未返回 code_list | 只建立低置信明细，进入待核准。 |
| 大小码关联 | 52563 展开后与应录码集合存在唯一交集 | 归入对应明细并记录 relation_match。 |

### 4.6 抢单和占用

抢单用于处理多条对码核准明细同时命中同一条系统单明细的情况。

- 候选不等于占用；只有完成唯一高置信匹配、且当前全量核准通过的准入库明细，才能软占用 remaining_qty；
- 用户核准完毕或入库后，记录已选系统单及占用关系；
- 同任务内后出现的候选证据集合更高，且 score 分差 >= 15 时，可替换原“仍达到软占用门槛、但相对证据更弱”的软占用；原明细释放占用并回到待核准；
- 用户已确认的候选不因普通自动重算被抢走，但其依据被删除、候选失效或产生硬冲突时，必须重新校验；
- 用户核准完毕后，软占用转为人工确认占用；换候选时旧占用释放和新占用建立必须一次完成，失败时不改变原占用；
- 同一系统单明细的累计占用不得超过 remaining_qty，超出部分进入待核准；
- 核准页候选需展示已占用数量和剩余可入库数量。

### 4.7 删除、修改和重算

以下操作不是只改页面展示，必须按真实数据重新计算：

| 操作 | 重算范围 |
| --- | --- |
| 新增/删除追溯码 | 应录实录、对码核准明细聚合、两个候选集、评分、核准项、软占用、状态卡。 |
| 新增图片/OCR 成功 | 拍单明细、待验货、随货单候选、核准项、状态卡。 |
| 删除图片/清空图片 | 删除对应拍单明细，释放其匹配关系，重算所有受影响明细和状态卡。 |
| 换系统单/拍单候选 | 当前明细的匹配结果、全量核准、占用和状态。 |
| 编辑追溯码/批次 | 当前明细的归属、匹配、冲突和状态。 |
| 标记/取消破损 | 当前明细核准状态。 |
| 系统单状态、剩余数量变化 | 受影响候选、抢单占用和核准状态。 |

删除最后一个实录码时，释放该明细占用；若该明细没有其他有效依据，移除正常聚合结果，并根据剩余异常决定是否保留异常明细。

重算应在同一结果版本内完成候选、评分、占用、明细状态和卡片更新；重算失败时保留上一个完整结果并提示重试，不能只更新其中一部分。

已入库明细仍允许继续操作并触发重算。但同一聚合 key 已有入库结果后新增追溯码，是追加原明细还是生成新的处理轮次；删除或修改如何影响已落库存、是否生成冲销或纠错记录，当前尚未确认。本版不预设答案。

## 5. 页面需求

### 5.1 任务列表

| 区域/操作 | 需求 |
| --- | --- |
| 新建任务 | 创建任务并进入拍单页。 |
| 列表字段 | 入库任务单号、任务创建日期、最近操作日期、待验货、待核准、准入库、已入库、采购单号/供应商、操作。日期格式 YYYY-MM-DD。 |
| 最近操作日期 | 当前任务最近一次在服务端提交成功，且真实改变业务数据或处理状态的日期。 |
| 筛选 | 支持任务单号、采购单号、供应商、商品信息、创建日期范围、最近操作日期范围；支持清空。 |
| 进入任务 | 恢复已有图片、追溯码、匹配、核准和入库结果。入口统一为“进入”。 |
| 任务状态 | 不提供结束、关闭或自动完成；提交入库后仍可再次进入并继续操作。 |

无结果时显示空状态，不保留旧筛选结果。采购单号/供应商存在多值时的展示规则见第 9 章待确认。

### 5.2 拍单页

拍照画面是本页主内容，应占最大可视面积。已拍图片、上传、删除和状态卡紧凑放置，不单独占用大块区域。

页面横向排布：取景区占主区域；已拍票据位于取景区右侧，单列逐张展示并纵向滚动；状态卡位于最右侧，不被票据列表挤到页面底部。

| 区域/操作 | 需求 |
| --- | --- |
| 高拍仪/拍照 | 展示实时画面，拍照后上传并发起 OCR。 |
| 本地上传 | 支持 PNG、JPG，单张不超过 10MB；不符合时不上传并提示原因。 |
| 识别中 | 图片显示“识别中”，不提前计入有效拍单明细。 |
| 识别成功 | OCR 完成、拍单明细落地且受影响匹配重算完成后，显示“识别成功”。 |
| 识别失败 | 自动删除本次失败图片，提示“OCR识别错误，请重新拍照上传”。 |
| 图片列表 | 展示已成功图片数量和缩略图；按 OCR 页码升序，同页按上传时间排序；无页码显示“无页码”并排在有页码图片之后。 |
| 删除单张 | 删除图片及对应拍单明细，并重算。是否二次确认见第 9 章。 |
| 清空全部 | 删除任务内全部图片及拍单明细，并重算。是否二次确认见第 9 章。 |

低置信 OCR 行允许进入候选，但核准页必须标识低置信，不能自动进入准入库。

### 5.3 验货页

扫码画面、已录入对码核准明细和核心状态需在首屏可见。搜索、追溯码管理等次要操作贴近明细列表。

| 区域/操作 | 需求 |
| --- | --- |
| 扫码取景 | 持续识别一个或多个追溯码，逐码执行单码验货逻辑。 |
| 识别反馈 | 展示本次识别码和处理结果；命中已有明细时置顶、高亮。 |
| 明细列表 | 展示商品名、规格、批准文号、批号、效期、实录/应录、核准状态。列表可持续增长并滚动。 |
| 搜索 | 支持按商品名、规格、批准文号、批号、效期、追溯码搜索。 |
| 追溯码管理 | 展开完整码列表；允许删除，删除后立即重算。 |
| 破损待采退 | 标记后进入待核准；取消后重新计算。 |
| 扫描异常 | 保存原始码，展示失败阶段和简明原因，不丢弃。 |

复杂的系统单候选、随货单候选和三方字段差异放在核准页，不占用验货主画面。

步骤门槛：没有 OCR 成功的拍单明细时，不能进入验货；提示先拍摄或上传随货单。OCR 仍在处理中时不视为成功。

### 5.4 核准页

核准页以“当前待处理明细 + 三方证据 + 决策操作”为主，队列和状态卡不应挤压核心核对区。

| 区域/操作 | 需求 |
| --- | --- |
| 进入页面 | 显示简短加载态“正在匹配系统单和随货单”，完成后进入工作台。 |
| 待核准队列 | 展示待核准数量、异常标签和搜索；默认选中队首。 |
| 入库信息 | 展示供应商、商品、系统单号、批号、效期、实录/应录、追溯码入口和当前状态。 |
| 三方证据 | 同屏展示码上放心/实物、掌店易系统单、随货单 OCR；异常字段优先，支持展开全部。 |
| 美团商品信息 | 按 Demo 展示商品名、批准文号、厂家、处方分类和商品图片，作为人工辅助信息。是否参与自动核准待确认；未确认前不参与。 |
| 系统单候选 | 展示系统单号、供应商、商品、规格、剩余数量、已占用数量、分数和命中证据。 |
| 随货单候选 | 展示拍单明细字段和对应局部截图，支持放大。 |
| 换候选 | 用户选择后触发当前明细全量重算。 |
| 核准完毕 | 当前明细进入准入库，自动切换下一条。 |
| 留在待核准 | 当前明细仍为待核准，排到待核准队尾，自动切换下一条。 |
| 提报异常 | 记录异常原因，保留待核准。 |
| 提交入库 | 只在用户主动操作时提交准入库明细；成功转已入库，失败留在准入库并展示明细级原因。 |

步骤门槛：没有对码核准明细且没有扫码异常记录时，不能进入核准，提示先完成验货扫码。52560 多单、找不到上游明细等异常在核准页展示原始码、失败阶段和已有候选，人工处理动作见第 9 章待确认。

“核准完毕/留在待核准”只显示在当前选中的队列项。核准完毕保留投向准入库卡的结果反馈；留在待核准只播放当前队列卡移动到队尾的动画，不触发待核准卡或轨道发光。动画不得阻塞状态落库。

### 5.5 状态卡

- 顺序与 Demo 一致：已入库、准入库、待核准、待验货；
- 四卡计数严格使用第 3.2 节口径；
- 若保留轨道比例，按当前四卡显示数字计算，仅表达当前工作量分布，不表达任务完成度；
- 卡片与主内容等高对齐，避免外框套内框和底部空白；
- 四张卡均保留点击入口；点击后的详情页需求不在本版展开。

## 6. 异常和边界

| 场景 | 处理 |
| --- | --- |
| 52560 无上游单据 | 保存原始码和接口结果；后续承载对象、是否计入待核准待确认。 |
| 52560 返回多个上游单据 | 不自动选单，保存候选；后续人工处理方式待确认。 |
| 53727 查询失败 | 保留已获得的单据线索和错误信息，允许重试；失败记录如何进入核准待确认。 |
| 53727 明细找不到扫描码 | 调用 52563 查大小码；仍无唯一交集时保存异常，后续人工处理方式待确认。 |
| 52566 有商品信息但无上游单据 | 只展示基础商品信息，不自动进入准入库。是否允许人工入库待确认。 |
| 69631 返回码未激活/不存在 | 标记高风险，不计入正常实录，进入待核准。 |
| 系统单多候选 | 展示候选和证据，不直接取最高分放行。 |
| 系统单无候选 | 进入待核准，允许换候选或提报异常。 |
| 随货单多候选/无候选 | 进入待核准，允许换拍单明细或提报异常。 |
| OCR 低置信 | 允许作为候选，明确标识，不自动放行。 |
| 准字缺失 | 使用名称、规格、厂家、批号、数量召回弱候选，不凭弱证据自动放行。 |
| 系统单批号为空 | 不因缺失直接排除候选；核准页展示缺失，按其他证据判断。 |
| 数量不一致 | 展示应录、实录、拍单数量和系统单剩余数量，进入待核准。 |
| 入库部分成功 | 以对码核准明细行为结果粒度：成功行转已入库，失败行留在准入库；重复提交不得重复入库。两行组合内部部分成功另行确认。 |
| 刷新/切换页面 | 从服务端恢复任务数据，不丢失图片、码、候选、核准决策和入库结果。 |

## 8. 验收标准

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| AC-001 | 同一任务持续新增图片、扫码并多次入库 | 任务不自动结束，仍可进入和继续操作。 |
| AC-002 | OCR 成功产生 6 行，2 行已被对码覆盖 | 待验货显示 4；其他三卡不按拍单明细计数。 |
| AC-003 | 一条准入库明细提交成功 | 准入库 -1、已入库 +1，均按对码核准明细行计算。 |
| AC-004 | OCR 服务返回失败 | 失败图片自动删除，不产生拍单明细、不增加待验货，提示“OCR识别错误，请重新拍照上传”。 |
| AC-005 | 同一任务重复扫描同一码 | 不重复计数，定位原明细。 |
| AC-006 | 尚未入库的同一上游明细再次扫到新码 | 追加到原对码核准明细，实录数量和全部核准结果重算。 |
| AC-007 | 53727 未直接命中，52563 得到唯一关联 | 归入对应明细并记录 relation_match。 |
| AC-008 | 系统候选属于 A-D、score >= 85、分差 >= 15 且无硬冲突 | 系统单判定为唯一高置信候选。 |
| AC-009 | 最高候选 score >= 85 但分差 < 15 | 进入待核准，展示多候选。 |
| AC-010 | 最高候选 score < 60 | 判定无可靠匹配，进入待核准。 |
| AC-011 | 仅一条弱证据线命中 | 只进入人工候选，不自动放行。 |
| AC-012 | 满足同单、同商品、同批号、两行数量合计相等 | 允许两条系统单明细组合；任一条件不满足不得组合放行。 |
| AC-013 | 实录少于应录 | 待核准并提示还差 n 个追溯码。 |
| AC-014 | 删除图片或追溯码 | 受影响候选、评分、冲突、占用、明细状态和卡片数量全部重算。 |
| AC-015 | 点击“留在待核准” | 当前明细排到待核准队尾，待核准数量不变，并自动切换下一条。 |
| AC-016 | 明细自动进入准入库 | 只更新状态，不自动调用入库服务。 |
| AC-017 | 存在待验货/待核准，同时有准入库明细 | 用户仍可主动提交准入库明细。 |
| AC-018 | 入库接口按明细行部分成功 | 成功行进入已入库，失败行留在准入库并展示原因。 |
| AC-019 | 后出现的强候选达到抢单条件 | 替换较弱软占用，释放原占用，原明细回待核准，累计占用不超 remaining_qty。 |

## 9. 待确认

以下问题当前资料不足，本文不预设答案：

### 9.1 阻断开发

1. 两行组合提交时，一行成功、一行失败如何处理？是否要求组合内原子成功，整条对码核准明细再转已入库？
2. 同一 bill_code + drug_ent_base_info_id + product_batch_no 已有入库结果后继续扫码，是追加原明细、生成新处理轮次，还是按新增数量生成新明细？四卡分别怎么计？
3. 评分细则：供应商名称弱匹配加多少分；批号/效期只命中一项如何计分；字段缺失、归一化、并列和小数精度如何处理？
4. 无法定位码上放心明细的追溯码，是否生成异常对码核准明细并计入待核准？用户可做哪些处理？
5. 拍单明细只被部分数量覆盖时，是否仍计待验货？一条拍单明细能否对应多条对码核准明细？

### 9.2 业务规则

6. 系统供应商未绑定码上放心 ref_ent_id，仅名称相似时，是否允许自动进入准入库？
7. 没有可靠随货单 OCR 行，但码上放心和系统单完全一致时，是否允许进入准入库？
8. 单价、金额差异是否阻断入库，还是仅提示？
9. 近效期、过期的判定阈值和处理方式是什么？
10. 编辑追溯码/批次、手工选择无可靠候选、人工覆盖硬冲突、提报异常是否需要主管权限和必填原因？
11. 找不到上游单据但 52566 有商品资料时，是否允许人工核准入库？
12. 已入库明细删除或修改后，实际库存如何纠错，是否生成撤回/冲销记录？
13. 跨任务、跨门店和已入库历史中的重复追溯码如何提示和拦截？
14. 提交入库是提交全部准入库，还是由用户勾选部分？提交前是否强制重校验剩余数量和占用？

### 9.3 页面规则

15. 任务列表中的采购单号/供应商有多值时，展示首个、最近一个还是“名称等 n 项”？
16. 删除单张图片、清空全部图片是否需要二次确认？触发条件是否区分“已有下游匹配结果”？
17. 待核准队列只有一条时，点击“留在待核准”后是否立即再次选中？何时重新提醒？
18. 美团商品信息只做人工辅助，还是参与自动核准？取数失败是否阻断？
19. OCR 低置信使用服务端标志还是数值阈值？是否支持编辑字段、排除非商品行、拆行/合行和重新识别？
20. 四卡混合两种统计对象，轨道比例是否继续保留？如保留，仅表达工作量分布是否符合预期？
