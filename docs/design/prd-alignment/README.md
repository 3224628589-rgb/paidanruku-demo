# 《入库提效三期 拍单入库》Demo 对齐交付说明

## 1. 交付模式与准则

- 交付模式：`project-native-preview`，直接修改现有 `index.html + app.js + styles.css` Demo。
- 第一准则：仓库根目录最新稿 `入库提效三期 拍单入库新.docx`（23 页、15 张嵌图）。
- 对比基线：旧稿 `入库提效三期 拍单入库.docx`（17 页、14 张嵌图）。
- 辅助材料：用户后续明确的卡片计数和进度共享口径、Figma `线上铺货` 节点 `363:90` 的四个核准辅助弹窗。
- 不作为反向准则：`AI版需求文档`、讨论稿数据模型、当前实现中的演示捷径。
- 冲突处理：Word 与用户后续明确口径冲突时保留后续已确认口径，并在“模糊边界”中显式登记；不得静默二选一。

## 2. 业务模型结论

入库任务是操作会话。随货单 OCR 明细提供“票”，码上放心验货信息与实录追溯码提供“实”，系统采购明细提供“账”。系统分别生成随货单候选和系统单候选，实时核准后把商品卡分流到待验货、待核准、准入库、已入库四个状态；人工核准只改变当前商品卡的状态，不创建新的采购数量。

当前 Demo 延续用户已经明确的 UI 计数口径：

- 待验货：按尚未发生实物命中的 OCR 明细行计数，一行只算一张卡，不使用该行采购数量。
- 待核准、准入库、已入库：按实录追溯码逐件生成核准卡，每张卡数量固定为 1。
- 验货列表：按票据归属、商品和批次聚合展示；卡片内保存多条实录追溯码。
- 三页进度：读取同一业务状态投影，切换拍单、验货、核准不重置数字。

## 3. Discovered UI Constraints

- PC 横屏是唯一验收形态；主工作区必须优先于标题、说明和装饰。
- 左侧步骤导航固定，右侧“提报异常 + 四状态卡 + 四段轨道”在三页结构、尺寸和数据完全一致。
- 拍单页高拍仪取景框是最大视觉主体；票据列表保持单列纵向管理。
- 验货页保留扫描取景框与已录入品批双主区；不得把验货卡改成核准证据卡。
- 核准页固定为左侧待核准队列、中部证据详情、右侧共享进度；蓝卡、黄卡、三方对比上下同轴。
- 短时 OCR、扫码分组处理、删票重匹配期间整页锁定，避免状态在处理中被并发修改。
- 只有业务数量真实增加时触发进度卡弹动或轨道发光；“留在待核准”只做队尾移动。
- 原稿未定义的结果页、算法解释页和营销说明不加入当前工作流。
- 本期所有有效验货明细均有码上放心资料兜底；“没有找到商品信息”不属于本期页面状态。
- Figma 弹窗按原稿信息层级复刻，尺寸使用视口比例和最大高度约束，不能把 Figma 组合画布像素直接写入页面。
